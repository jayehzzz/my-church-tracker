# Follow-up delegation programme — Task 1 API and ownership

Implemented 3 October 2026 on shared branch `codex/follow-up-delegation`, starting from clean, up-to-date `main` at `2e1f247`. Tasks 2 and 3 continue this branch sequentially. Owner acceptance and production release are separate gates.

## Assignment contract

- `crm:getAssignmentDirectory({})` is approved owner/admin-only. Returns all non-archived people with minimal identity/status fields, current `assignment_id` (null if unassigned), `assigned_leader_id`, `assigned_leader_name`, `blocked_reason` and `open_follow_up_count`. This list is independent of Follow-up's date and worker filters. It does not grant leaders churchwide discovery. Recipient leaders are existing people with `member_status: leader`.
- `crm:assignContact({personId, assignedLeaderId, expectedAssignmentId?, createFirstContactTask?, firstContactDueDate?, reason?})` remains the compatibility API for assigning any eligible person. Owner/admin authority is enforced by the existing secured mutation wrapper. The trusted account is the audit actor; caller-supplied actor IDs do not establish authority.
- Pass `expectedAssignmentId: null` for a reviewed unassigned person or the current assignment ID for a reviewed assigned person. A changed assignment rejects the entire person's transaction. Legacy callers may omit the guard; the new assignment panel always supplies it. Repeating the same assignment is idempotent; legacy duplicate active assignments are ended. History rows are retained.
- `followUpCrmService.assignContact(personId, leaderId, dueDate, options)` forwards the guard. `batchAssignContacts(ids, leaderId, dueDate, {expectedAssignments})` processes unique people sequentially and returns `data`, `succeededPersonIds`, `errors: [{personId,error}]`, and an aggregate `error` on any failure. Each person's transaction is atomic; a partial batch keeps successful writes and reports every failure. The panel clears successful selections and keeps failed selections for review. Refresh clears reviewed selections and loads fresh versions.
- The new Follow-up **Assignments** panel sends `createFirstContactTask: false`; delegating responsibility never implicitly schedules work. Existing outreach assignment controls retain initial first-contact scheduling. Members/leaders never receive an outreach first-contact task. Reassignment never restarts first contact, changes its due date, or edits membership or outreach state.
- Paused, archived and do-not-contact people cannot be assigned through this mutation. Paused people require the existing explicit reactivation workflow; assignment does not reactivate them. Restricted people are visibly disabled in the directory; archived people are excluded.

## Outstanding work and history

Within the assignment transaction, `replaceAssignment` transfers **open** general `first_contact`, `follow_up`, `sunday_confirmation` and `reengagement` tasks to the new responsible leader. The shared `isDelegatedFollowUpTask` predicate excludes tasks linked to a programme, meeting or visitation, and excludes `member_care`, `visitation` and `other`. Independent responsibilities and their existing access checks remain intact.

Transferred tasks keep their IDs, dates, reason, priority, automation keys and links. Append-only `ownership_history` records `from_leader_id`, `to_leader_id`, `assignment_id`, and `at`; the secured database wrapper also records the authenticated audit actor. The optional schema field requires no data migration. Completed and cancelled tasks, recorded calls, Sunday commitment/attendance-plan rows and response history are not rewritten. Previous assignments have `status: ended` and `ended_at`; the person drawer exposes current and previous assignment history through `getContactProfile.assignment_history`.

The new leader's active assignment grants the existing scoped person access, and transferred task ownership grants task mutation authority. The previous worker cannot complete a transferred task even if they retain bacenta access. Reassignment does not change bacenta membership, inviter attribution, care/visitation ownership, actual attendance, or Sunday responses.

## Contract for Task 2

Use active `follow_up_assignments` as the responsibility source for members, leaders and non-members; do not infer it from inviter, bacenta membership, last caller or historical `gathering_commitments.leader_id`. Keep recorded Sunday actor attribution as history. Current dashboard Sunday/upcoming commitment filtering now uses the active owner with recorded-worker fallback only where there is no assignment; worker assessment history remains attributed to its original recorded worker. Task 2 should derive permanent leader lists from the active assignment, including people without dated confirmations, and keep explicit Sunday responses separate from ownership.

Do not schedule missing member tasks or count a person as expected just because they were assigned. Do not rewrite Sunday responses when ownership changes. Shared Practice database is `standing-mongoose-699`; opening or deploying functions must preserve records. No refresh/import/reset was authorized.

## Task 2 — permanent Sunday confirmation lists (3 October 2026)

The active assignment is the permanent responsibility source. `crm:getDashboard.sunday_confirmation_roster` includes each eligible member/leader and contact/non-member once, even without a dated response. Approved leaders receive only their currently assigned people; an explicit filter for another leader is rejected. Owner/admin queries can show everyone (including unassigned people) or filter by current leader. Bacenta membership and inviter attribution never supply ownership for this list. Paused/do-not-contact rows remain identifiable but cannot receive new responses. Assignment does not schedule a task or create attendance.

Each row contains `assignment_id`, `assigned_leader_id`, `assigned_leader_name`, `sunday_response` (`not_contacted`, `yes`, `maybe`, `no`, or a retained explicit `cancelled` Yes), `sunday_commitment`, `attendance_plan`, `response_updated_at`, dated `response_note`/`response_note_at`, `actual_result`, and `contact_blocked`. Notes from legacy confidential member plans are not aliased into unrestricted response fields. Existing privacy redaction still applies to person fields and plan notes. The shared pure selector is `src/lib/services/sundayConfirmationLogic.js`; it deduplicates by person/date using updated time and creation order. A newer invalidated legacy duplicate cannot revive an older Yes.

`crm:recordSundayResponse({personId,leaderId,serviceDate,response,note?,expectedAssignmentId,expectedResponseVersion})` records Yes/Maybe/No on a valid Sunday. Use the row's assignment ID and `sundayResponseVersion(row.sunday_commitment,row.attendance_plan)`. The version includes the reviewed commitment/history state and member plan, so same-millisecond changes still conflict. The secured wrapper pins leader actors to their account; the mutation verifies the current owner and both versions. It rejects unassigned/reassigned people, restricted contacts, stale responses, and Sundays with attendance results. Changing a pending Yes to Maybe/No keeps the cancellation entry and stores the new explicit response. A later Yes reconfirms that same dated record; corrections/entered-in-error and their history remain intact. Member responses also synchronize the compatibility attendance plan (`confirmed`/`expected`/`away`); the legacy `expected` plan value alone is never confirmation. No data migration is required.

Follow-up → Sunday and My Bacenta → Sunday share the list UI, response form, dated notes and state filters. The owner can open the existing Assignments panel for assignment gaps. My Bacenta's permanent list follows explicit assignments across programmes; its other bacenta people/work views keep their original scope. Actual result/correction/history controls remain separate. Switching Sundays clears old evidence before loading; a response from one Sunday is never copied to another.

### Contract for Task 3: confirmed versus expected versus attended

- `confirmed_total` and `confirmed_members`/`confirmed_guests` count unique people with a dated pending Yes (or a legacy confirmed member plan where there is no contrary response). A member's legacy commitment without a plan is supported. An uncontacted assignment, Maybe, No, cancellation, invalidated response or resolved actual result adds no confirmation.
- At Task 2, `attendance_forecast.total_expected`/normalized `expected_total` and `expected_person_ids` contain only those named confirmed people. Assignment itself is not an expectation. Task 3 may add separately identified expected guests; it must keep confirmed counts unchanged, deduplicate named people, and distinguish unnamed headcounts.
- Actual attendance comes only from the explicit church-register/attendance workflow. The list's `actual_result` is display evidence; saving a response never creates a check-in, no-show, care task, or follow-up task. A cancelled confirmation is not a recorded absence. Sunday result summaries now exclude cancellations from missed counts.
- Keep the shared branch and pinned Practice backend. No refresh/import/reset or production release is authorized. Authenticated owner/leader Practice acceptance is a separate gate from implementation completion.

## Task 3 — expected guests without outreach (3 October 2026)

`guest_invitations` stores one dated invitation independently of people, outreach, personal Sunday responses and actual attendance. An unknown friend has an inviter and a numbered display label; that label is never saved as a person's name. Known guests may keep optional contact details in the invitation until an owner/admin explicitly links an existing person or creates a normal non-member record. Creation sets no contact date/source, first visit, salvation or membership milestone. An invitation's responsible leader is separate from permanent person assignment; it does not grant access to unrelated people.

`expectedGuests:create`, `update`, `link` and `attendance` are approved owner/admin-only. Updates and links require `expectedVersion` and a correction reason, append before/after history, and reject stale writes. Assigned approved leaders can read their invitation list; other leaders, viewers and unapproved users cannot discover it. Linking checks existing normalized phone/email duplicates, active/restricted people and self-invitation; it preserves the invitation's inviter and an existing person's attribution. Person merge moves references with history; permanent deletion is blocked while invitation references exist.

`crm:getDashboard.guest_invitations` follows the selected Sunday and invitation leader filter. Reported coming adds unique invitation identities to `expected_total`; tentative, cancelled, invalidated, archived, attended and explicit non-arrivals are excluded. Linked person IDs deduplicate against other invitations and independent pending Yes responses. `confirmed_total` and the member/guest confirmed counts retain Task 2 semantics. `expected_guest_invitation_ids`, `additional_expected_guests`, `unnamed_expected_guests` and `tentative_guest_count` provide matching evidence. An invitation cancellation does not silently erase an independently recorded personal Yes; review those responses separately when the plan changed.

Actual named attendance requires a real linked person and explicit selection of the matching Sunday service through the existing register workflow. An unknown invitation cannot create a fictional named check-in or inflate unnamed service totals. Service/attendance edits and removal reconcile the display attendance link and retain the original invitation date/history. Non-arrival is an explicit result after Sunday, never inferred from a tentative invitation. Correcting actual attendance requires a reason and a chosen invitation state; the original personal response remains a separate record.

Follow-up → Sunday supports creation, details/status corrections, existing/new person linking and invitation history. My Bacenta exposes a read-only list for the assigned leader. Connected errors remain errors; the explicit local demo path never substitutes for failed live requests. Existing invitation/Practice data requires no migration, copy or reset. Authenticated Practice owner/leader acceptance and any production release remain separate gates.
